## 二、七阶段模型（业界共识）

综合多个来源（FDE Academy、360digitaltransformation、cloudsoftsol）后，这个阶段划分基本一致：

| 阶段 | 时间参考 | 核心内容 | 标志性产出 |
|------|---------|---------|-----------|
| **1. 理解 FDE 岗位** | 第 1–2 周 | FDE 负责什么、与 SE/SA/顾问的区别、为什么 AI 试点会失败 | 能讲清这个岗位的价值 |
| **2. 软件工程地基** | 第 1–3 月 | Python（主力）、SQL 与数据建模、REST API、Git、测试 | 能独立交付一个小服务 |
| **3. 数据与系统集成** | 第 2–4 月 | 脏数据治理、ETL/ELT、Schema 设计、Webhooks、gRPC | 能连两个 API 并处理真实数据 |
| **4. 应用 AI 与 LLM 工程** | 第 3–6 月 | LLM API、结构化输出、Embedding 与切分、向量库、生产级 RAG、**评测框架**、Agent 与工具调用、LangGraph / LangChain / CrewAI、MCP、护栏 | 能构建生产级 RAG + 评测流水线 |
| **5. 部署、云与运维** | 第 5–8 月 | FastAPI、Docker、云部署、IAM 与密钥、OpenTelemetry 可观测、成本与延迟控制、AI 红队（提示注入 / OWASP LLM Top 10）、CI/CD | 能把服务安全部署上线 |
| **6. 客户交付技艺** | 持续 | discovery 会话、拆解模糊性、方案架构、干系人沟通、POC → 生产交接、上线后推动采纳 | 能独立主导一次客户交付 |
| **7. 作品集与求职** | 最后 6–8 周 | 3+ 个可辩护的部署系统、案例分解练习、企业系统设计、5 个 STAR 行为故事 | 可投递的完整作品集 |

### ⚠️ 关键提醒（来自 alphalab.site 的实践总结）
> 「在没有 AI 知识之前先学扎实后端代码」是绝大多数人的第一个陷阱。
> 很多生产级 GenAI Bug 本质是普通 Bug —— 超时、畸形 payload、缺重试、查询没索引。

### 阶段 4 的「评测」为何被反复强调
Dexity 与多个来源都把 **evaluation harness** 列为 FDE 的分水岭能力：
> 「prove it, don't claim it」（证明它，而不是声称它）

Alphalab 的完成标准很具体：`evals/results.json` 必须能呈现**基准、版本变更、错误分类**三项。

## 四、90 天与 12 周加速计划

### 90 天计划（后端/ML 工程师转型）
来源：[rishabhsaini282/forward-deployed-ai-engineer-data](https://github.com/rishabhsaini282/forward-deployed-ai-engineer-data)

| 阶段 | 天数 | 目标 |
|------|------|------|
| Phase 1 | 1–30 | 生产工程地基：Python + SQL 到生产深度；企业云 IAM（跨账号角色、VPC 对等、密钥管理） |
| Phase 2 | 31–60 | 应用 AI 与上下文管理：企业级 RAG（父子文档、稀疏-稠密混合检索、recall@k / MRR）；自动化评测框架（DeepEval / LangSmith / Arize）；OWASP LLM Top 10 |
| Phase 3 | 61–75 | 客户工程姿态：范围与模糊性拆解；**遗留系统模拟**（老 ERP 导出、过时本体、代理层） |
| Phase 4 | 76–90 | 作品集与面试：Capstone 项目含 RAG 流水线 + CI/CD 每次提交跑评测 + **系统分解文档** |

> Phase 4 的分解文档才是向招聘方传递「企业级成熟度」的信号。

### 12 周节奏（中文圈实践版）
来源：[alphalab.site](https://www.alphalab.site/forward-deployed-engineer)

| 周次 | 痛点 | 解法 | 完成标准 |
|------|------|------|-----------|
| W1–3 | 作品只有 Notebook，展示不了 API/部署/权限/运维 | 做带 API、Postgres、登录、测试、logs 的普通 Web 服务 | 服务部署上线，错误可被记录 |
| W4–6 | AI 偶尔答对，但说不清何时失败 | 结构化输出、工具调用、覆盖代表性失败模式的测试集、trace、timeout、retry、人工 fallback | `evals/results.json` 呈现基准、版本变更、错误分类 |
| W7–9 | 解的是自己想象的问题 | 找一位真人使用，观察完整流程，写 discovery-brief.md | 对方能指出哪一步省时间、哪一步仍要人工 |
| W10–12 | Demo 通过但真实使用卡在权限与例外 | 接真实数据源 + 既有工具，先跑 shadow mode，补 audit log、runbook、rollback、一次事故演练 | 交接后你不在场也能处理常见故障 |

> **核心原则**：不是 12 周转职保证，而是一套**做出第一个真实部署案例**的交付节奏。

## 六、学习路径选择建议

**如果你是**后端/全栈工程师（有 1–3 年生产经验）
→ 直接走 Awesome-FDE-Roadmap，重点补**客户工程技艺**（阶段 6），技术地基你已经有了

**如果你是** ML/AI 工程师
→ 重点补**云 IAM、生产部署、评测体系**（阶段 5），你的模型能力可能领先但工程落地经验不足

**如果你是**前端/产品/设计背景（转行跨度大）
→ 先读中文三本手册建立图景 → 认真补阶段 2（Python/SQL/API）→ 用 90 天计划里的 capstone 强制产出

**如果你是**PM / 咨询顾问
→ 你的优势是 discovery 与拆解能力，缺的是生产代码能力。阶段 4 和 5 必须亲自写代码过一遍
→ 参考 [xinnan-tech/xiaozhi-fde-talk](https://github.com/xinnan-tech/xiaozhi-fde-talk) 这类需求访谈辅助工具
