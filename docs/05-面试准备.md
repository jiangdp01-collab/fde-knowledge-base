# 05 · 面试准备

> FDE 面试考的东西和普通 SWE 面试**几乎不重叠**。LeetCode 占比很低，核心是「在模糊中交付」的能力。

---

## 一、三轮面试结构（业界共识）

来自 Dexity 对 187–191 份 JD 的分析：

| 轮次 | 时长 | 考什么 | 信号 |
|------|------|--------|------|
| **1. 行为与姿态筛查** | 45–60 分钟 | Ownership 在范围模糊时的表现、高摩擦干系人管理、韧性 | **不是文化匹配筛查** —— 测的是「你能否在敌意 CTO 面前守住立场同时保住关系」 |
| **2. 技术深挖** | 2 轮 × 60–75 分钟 | R1：现场 API 编排、云 IAM 配置、数据解析；R2：混乱企业迁移或数据本体问题的系统设计 | **基本不考 LeetCode** |
| **3. 分解案例 + 客户模拟** | 未披露时长 | 给一个模糊的企业问题，现场演示如何隔离真问题、划 MVP 范围、绘制技术风险图 | 部分实验室会加**现场客户模拟**，面试官中途挑战你的架构 |

> ⚠️ 部分岗位的题干会明确「这不是文化匹配筛查」。
> Dexity 原话：*"they're testing whether you can hold ground with a hostile CTO while protecting the relationship."*

## 三、三轮分别怎么准备

### 第一轮：行为与姿态

**这轮真正在测的东西**：范围模糊时的 Ownership。

Colin Jarvis（OpenAI FDE 负责人）的话说明了日常工作的真实状态：
> *"FDEs work in a ton of ambiguity, and often what the customer describes in scoping doesn't match the data/system reality on the ground."*

**准备方向**：
- 准备一个**你曾经面对模糊需求**的案例，说明你怎么把它拆成可执行的范围
- 准备一个**你和客户/上级有冲突**的案例，说明你怎么既守住技术立场又保住关系
- 准备一个**你交付的东西没被采纳**的案例 —— 这类问题最能区分 FDE 候选人，因为它直指「对结果负责」

> ⚠️ 避免的答法：讲「我按时高质量完成任务」。这与 FDE 的价值主张无关。

### 第二轮：技术深挖

**R1（现场操作类）**：
| 考项 | 具体内容 |
|------|---------|
| 现场 API 编排 | 给定几个 API，现场串成一个工作流 |
| 云 IAM 配置 | 跨账号角色、VPC 对等、密钥管理 —— 「如果你的应用无法安全访问防火墙后的数据库，模型能力毫无意义」 |
| 数据解析 | 脏数据、遗留格式、schema 不一致 |

**R2（系统设计类）**：混乱的企业迁移或数据本体挑战。

**必备知识清单**（来自 rishabhsaini282 的分析）：
- **企业级 RAG 模式** —— 不止基础 wrapper，要懂高级切分策略（父子文档关系）、稀疏-稠密混合检索
- **数学化评估检索** —— recall@k、MRR、hit-rate
- **自动化评测框架** —— DeepEval、LangSmith、Arize；构建 LLM-as-a-Judge 流水线，每次代码变更都跑连续回归
- **对齐 OWASP LLM Top 10** —— 提示注入、记忆投毒、数据外泄
- **遗留系统模拟** —— 老 ERP 导出、过时数据库本体、代理层构造、同意撤销适配器

**推荐**：[cma0232/genai-architecture-guide](https://github.com/cma0232/genai-architecture-guide) —— 明确标注为 FDE 与 Applied AI 面试的生产级 GenAI 架构指南。

### 第三轮：分解案例 + 客户模拟

**典型题面**（财富 100 银行合规自动化，来自 rishabhsaini282）：
> 一家财富 100 银行想部署 AI 代理以自动化内部投资组合合规审计。数据困在三台遗留主机中，合规参数每季度变化。设计部署策略。

**答题框架**：

**第一步：提出 discovery 问题**（不是直接给方案）
- 单份合规审计报告的基线延迟阈值是多少？
- 监管更新目前如何被人工合规团队接收？
- 能否在遗留主机环境上放一个安全 API 代理层，还是必须通过中间批量导出？

**第二步：MVP 框架**
- 提出局部化、只读的单监管框架文档抽取流水线
- 用历史审计报告建立**已验证的评测数据集**
- 之后再扩展到多州并行处理

> 💡 **关键理解**：这轮考的**不是技术方案本身**，而是你能否用提问隔离出真问题。考官想看你会不会一上来就讲 RAG 架构。

## 四、JD 里到底要求什么

Dexity 对 187 份 JD 的技能统计（这是最接近客观需求的答案）：

| 技能 | 出现率 | 说明 |
|------|--------|------|
| **Python** | 60% | 基线假设 —— 往往**根本不会写在 JD 里** |
| API 与系统集成 | 19% | 集成架构深度 |
| AWS / 云（GCP、Azure） | 17% | 云基线，广泛默认 |
| 数据管道 / PostgreSQL | 11% | 客户侧部署的数据深度 |
| React / 前端 | 10% | 部署可见性与客户工具 |

**AI 技能栈**（来自 Anthropic Applied AI FDE JD 与 OpenAI 的岗位说明）：
- LLM 生产技能 —— 高级提示工程、评测框架、规模化部署
- RAG 流水线 —— 切分策略、向量库（Pinecone、Weaviate、pgvector）
- Agent 框架 —— LangGraph、LangChain、CrewAI、DSPy；构建 MCP server 与 sub-agents
- 生产可观测性、安全与合规、提示架构
- **3 年以上**技术岗经验，或 SWE + 咨询经验

> ⚠️ 注意：60% 的 Python 出现率说明这个岗位**默认你会 Python**，而几乎所有 JD 都不会花篇幅教你怎么写生产代码。

## 五、面试前的准备清单

### 必备作品集结构
（来自 alphalab.site，中文社区已广泛采用）

```
fde-case-study/
├── discovery-brief.md        # 用户、触发事件、输入、输出、人工复核、不可碰的边界
├── architecture.md           # 架构与取舍
├── acceptance-criteria.md    # 哪些案例算通过、哪些风险必须回退人工
├── evals/
│   ├── golden-set.jsonl
│   └── results.json          # 基准、版本变更、错误分类
├── app/
│   └── runbook.md            # 运维手册
├── incident-postmortem.md    # 事故复盘
└── case-study.md             # 使用者、原流程、痛点、基准值、限制与非目标
```

> 💡 **case-study.md 首��要写**：使用者是谁、原流程是什么、痛点在哪、基准值是多少、**限制与非目标是什么**。
> 最后一项尤其重要 —— 说清「我不做什么」比说「我能做什么」更能体现企业级成熟度。

### 作品集能展示什么能力
来自 alphalab 的 12 周节奏完成标准，可以当作自检：
- [ ] 服务已部署上线，错误可被记录
- [ ] `evals/results.json` 能呈现基准、版本变更、错误分类
- [ ] 有真实使用者的反馈（对方能指出哪一步省时间、哪一步仍要人工）
- [ ] 跑过 shadow mode，有 audit log、runbook、rollback 机制
- [ ] 做过一次 incident 演练
- [ ] **交接后你不在场也能处理常见故障**

### 面试当天注意
- 准备**具体数字**：处理时长前后对比、人工复核率、错误率、单次成本
- 带一个**失败案例**：Demo 通过但真实使用卡在权限与例外的经历，比成功案例更有说服力
- 能说清一个系统**什么时候坏过** —— 证明你真的在生产环境待过
